## 6. Official price model และ gate ที่ implement แล้ว

`deriveBidWorkspace` ยังเป็นแหล่งคำนวณหลัก สมการเดิมยังอยู่ เพิ่ม `.official` projection ผ่าน `deriveOfficialPricing` ไม่สร้างสมการราคาอีกชุด

### ระดับ line

- มี `officialReview`: decision, sourceIds, comparisonId, locator, engineeringBasis, commercialBasis, reason, reviewer, date, basisKey
- decision: OPEN / KEEP / RECALCULATE / ADD / REMOVE
- ต้องระบุ customerRowCode ที่ mapping ถูกหมวด
- ต้องมี Current Tender evidence ที่มีเนื้อหาอ่านได้และ revision/authority ที่ใช้ได้ พร้อม clause/page, reason, reviewer/date
- ต้องมี requirementRef และ engineering/quantity/ownership กับ cost/commercial basis
- บันทึก Working ปกติไม่ได้ stamp review; ปุ่ม “บันทึกผลทบทวน OFF-03” จึงบันทึกฐาน review
- `officialLineBasisKey` ครอบ raw inputs, review fields (ยกเว้น key), offer, calculation, FX, referenced source records, comparison และ method `0550-official-review-v1`
- Input หรือหลักฐานที่เกี่ยวข้องเปลี่ยน → STALE ต้องตรวจใหม่
- Metadata-only, replaced/unconfirmed/conflicting evidence หรือ linked OPEN/CONFLICT finding ทำให้ไม่ผ่าน แม้มี review record
- Quote validity, duplicate ownership และ arithmetic gates เดิมยังทำงาน
- REMOVE แต่ยัง selected จะถูก block
- ผลคำนวณเก่าของ input ปัจจุบันแสดงได้ในฐานะ **Calculated candidate**; official amounts เป็น null/OPEN จนผ่าน review ไม่ fallback History

### ระดับ Customer row / Lot

- `customerReviews` เก็บ completeness review ของแต่ละ customer row
- ต้องตรวจ child lines ที่ selected และฐาน scope ของกลุ่มเอง
- Parent fingerprint ผูก children + line review + form + source/FX/decision
- EXCLUDED ต้องมี review/evidence และไม่มี selected child; EXCLUDED ไม่ใช่ศูนย์
- ไม่มี line หรือ child ยังไม่ผ่าน → OPEN
- รายการ selected ที่ mapping ไม่ถูก block totals
- Base A+B และ Options C แยกกัน; อย่าบวก C เข้า Base โดยอัตโนมัติ
- ผลรวมแถว selected ไม่เท่ากับตรวจ scope โครงการครบ
- `sumOfficial` สำหรับชุดว่าง/จำนวนไม่ครบคืน null ไม่ใช่ 0

### History comparison และ final release

- เปรียบเทียบ Customer Sell USD เฉพาะเมื่อ review ยืนยัน sameScopeAsHistory และ historySnapshotId ตรง พร้อมยอดทั้งสองด้าน
- ไม่ครบ → delta OPEN
- ส่วนต่างอาจมาจาก scope, quantity, rates, terms, FX ไม่ใช่ทุกส่วนต่างมาจาก RFQ revision
- Fingerprint เป็นตัวตรวจการเปลี่ยนข้อมูล ไม่ใช่ลายเซ็นอนุมัติหรือระบบสิทธิ์
- `releaseAllowed:false`, `releaseState:"HOLD"`; export ระบุ NOT ISSUED
- ถ้าเปลี่ยนความหมาย pricing/review ต้องพิจารณา bump method version และทบทวนใหม่

## 13. เทคนิคทำงานต่อใน Codex / GitHub

Local repo ของแชตนี้อยู่ detached HEAD; local SHA กับ remote SHA ต่างกันเพราะ publish ผ่าน GitHub Git-data APIs แต่ tested tree ตรงกัน อย่าสับสนว่า remote code ไม่ตรงเพียงเพราะ commit hash ต่าง

CLI push ครั้งแรกเคยติด auto approval review; ผู้ใช้ตอบ “ครับ อนุญาต” แล้ว ครั้งต่อมาพบ CLI ไม่มี GitHub username/credentials จึงใช้ connector ได้สำเร็จ ไม่ต้องค้นหา/เปิดเผย credentials

Publishing pattern ที่ใช้:

1. อ่าน remote ref ล่าสุดและ PR state
2. ทำ local commit เฉพาะไฟล์ของงาน ตรวจ git status/diff
3. GitHub `create_tree` จาก remote base tree + file contents
4. ตรวจ remote tree SHA เท่ากับ local `git rev-parse HEAD:`
5. `create_commit` โดยใช้ remote head เป็น parent
6. `update_ref` ด้วย expected_sha, force=false
7. อัปเดต PR metadata เมื่อ scope เปลี่ยน และตรวจผล

อย่าใช้ local original branch pointer ที่เก่าเป็นฐาน publish; อย่า force push เพื่อข้าม expected_sha mismatch ต้องอ่านและ reconcile งานใหม่ก่อน
